# 동시 부하 측정 (2026.08.23) — N-206이 Supabase Free에서 성립하는가

## 왜 쟀나

D-5는 「Supabase Pro 전환」을 필수로 적어 두었지만 **근거가 문서 어디에도 없었다.**
실측으로 하나씩 지우면 남는 이유가 하나뿐이었다.

| Free 한도 | 실측 | 판정 |
|---|---|---|
| DB 500MB | **21MB** | 무관 (4%) |
| 트래픽 5GB | 작은 행 몇 개 수준의 조회 | 무관 |
| 백업 없음 | 사용자 데이터 미저장 · 정적 자산 재적재로 복구(N-305) | 설계로 대체 |
| **1주일 무활동 시 정지** | 남은 일정의 최장 공백이 4일(9/3→9/7) | **조건 미달** |
| 공유 CPU · RAM 500MB | ← 이것만 미측정이었다 | **이 문서** |

## 측정 1 — DB 몫 (로컬에서 직접 질의)

판단 한 사이클이 DB에 거는 부하를 그대로 태웠다. 모델은 부르지 않는다.
`search_case` ×2(`word_similarity`로 360건 본문 훑기, 폴백 사다리 반영) ·
`check_documents` ×1 · `analyze_risk_pattern` ×1.

```
동시   세션당 p50    p95      최대     전체 벽시계
  1   0.08초    0.08초   0.08초   0.08초
  5   0.19초    0.32초   0.32초   0.32초
 10   0.19초    0.21초   0.21초   0.21초
 20   0.29초    0.44초   0.44초   0.44초
```

동시 10에서 세션당 p95 **0.21초** — 단독 대비 2.8배. 판단 사이클 100초 중
DB 몫은 **0.2%**다.

⚠️ 이 값은 **개발 머신에서 잰 것**이라 절대치가 프로덕션보다 낙관적이다
(Vercel↔Supabase 경로가 더 멀다). 읽을 값은 절대치가 아니라 **동시성이 올라갈 때
꺾이지 않는다**는 성질이다.

## 측정 2 — 프로덕션 실측 (`/precheck`)

사전 점검은 모델을 부르지 않고 DB만으로 도는 경로라 N-104(P95 **10초**)를
직접 검증한다. `precase.vercel.app`에 실호출.

```
단독      3.32초 (콜드 스타트) → 1.02초 → 1.00초
동시 10   0.89 · 1.93 · 2.24 · 2.38 · 2.86 · 2.86 · 2.90 · 3.09 · 3.09 · 3.14초
          p95 ≈ 3.1초 · 전체 벽시계 3.24초
```

**동시 10세션에서 P95 3.1초 — 목표 10초의 31%.** 여유 3배.

측정 1과 대조하면 3.1초 중 DB는 0.2초 남짓이므로, 병목은 Supabase가 아니라
Vercel 함수 기동·렌더다. **Pro로 바꿔도 이 숫자는 거의 그대로다.**

## 측정 3 — 이 시험이 결함을 잡았다 (접속 모드)

측정 1을 돌린 직후 다른 테스트가 깨졌다.

```
(EMAXCONNSESSION) max clients reached in session mode
                  - max clients are limited to pool_size: 15
```

`DATABASE_URL`이 **세션 모드 풀러(5432)**를 쓰고 있었다. 세션 모드는 클라이언트마다
연결을 붙들기 때문에 15개에서 막힌다. Vercel은 함수 인스턴스가 여럿이고 각자
`max: 5` 풀을 만들므로 **인스턴스 3~4개만 떠도 한도에 닿는다.**

Supabase 문서의 권고는 반대다.

> Use pooler transaction mode for application traffic from temporary clients
> (for example, serverless or edge functions).

**서버리스에 세션 모드를 쓴 것이 문서화된 안티패턴이었다.**

트랜잭션 모드(6543) + `prepare: false`로 바꾸고 다시 쟀다.

```
동시   세션당 p50    p95      최대     전체 벽시계
  1   0.19초    0.19초   0.19초   0.19초
  5   0.20초    0.37초   0.37초   0.37초
 10   0.34초    0.49초   0.49초   0.49초
 20   0.80초    0.84초   0.84초   0.84초
 50   1.95초    2.06초   2.06초   2.06초
```

**동시 50까지 오류 없이 완주**한다. 세션 모드가 막히던 15의 3배 이상이다.
전체 테스트 265건도 트랜잭션 모드에서 그대로 통과했다(세션 기능을 쓰는 코드가 없다).

⚠️ 트랜잭션 모드는 prepared statement를 지원하지 않으므로 `prepare: false`가 필수다.

## 측정 4 — 프로덕션 전환 후 (2026.08.23)

Vercel 환경변수의 포트를 6543으로 바꾸고 재배포한 뒤 다시 쟀다.

```
동시 25   200 25건 · 실패 0 · p95 3.04초
동시 40   200 40건 · 실패 0 · p50 3.22초 · p95 3.55초 · 최대 3.77초
```

동시 40에서도 **오류 0**이고 P95 3.55초로 N-104 목표(10초)의 36%다.
목표치인 동시 10세션(N-206)의 **4배**를 태워도 여유가 남는다.

⚠️ **정직하게 적어 둘 것** — 세션 모드에서 프로덕션 동시 40을 재본 적은 없다.
전환 전 프로덕션 측정은 동시 10까지였고 그때도 통과했다(P95 3.14초). 따라서
「전환으로 프로덕션이 살아났다」가 아니라 **「전환으로 연결 상한이 사라졌고,
그 상한은 로컬에서 15로 실측됐다」**가 정확한 서술이다.

응답 시간이 전환 전후로 거의 같다는 점도 같이 읽어야 한다(3.14초 → 3.04초).
**병목은 연결 모드가 아니라 Vercel 함수 기동**이며, 모드 교체가 고친 것은
속도가 아니라 **한계**다.

## 판단 경로는

모델이 100초를 쓰므로 DB 몫(0.2초)은 무시할 수준이다. 게다가 IP 레이트 리밋이
판단을 **일 10회**로 묶어서(N-203) 한 사람이 동시에 여러 판단을 돌릴 수도 없다.

## 결론

**동시 10세션(N-206)은 Free에서 성립한다.** Pro가 필요한 항목이 하나도 남지 않았다.

다만 **접속 모드를 고쳐야 한다.** 세션 모드로 두면 Pro를 사도 같은 벽에 부딪힌다 —
플랜이 아니라 모드의 문제이기 때문이다. 이 결함은 Pro 전환으로는 고쳐지지 않았을
것이고, 심사 중 동시 접속이 몰렸을 때 `EMAXCONNSESSION`으로 드러났을 것이다.

Pro를 산다면 그것은 성능이나 용량 때문이 아니라 **일 단위 백업**과 **로그 7일 보관**
때문이며, 둘 다 이 서비스에서는 약한 이유다(저장하는 사용자 데이터가 없다).

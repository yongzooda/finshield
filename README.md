# 프리케이스 (PreCase)

불완전판매 분쟁 예방·판단 AI 에이전트 — 2026 금융 AI Challenge 출품작

공개된 금융분쟁조정 선례와 법령을 개인의 사건에 대응시켜, 분쟁 발생 전에는 예방하고
발생 후에는 성립 가능성을 근거와 함께 알려주는 웹 서비스. 회원가입이 없고 상담 내용을
저장하지 않는다.

| | |
|---|---|
| 서비스 | https://precase.vercel.app |
| 검증 결과 공개 | https://precase.vercel.app/verification |
| 데모 3종 | https://precase.vercel.app/demo |

> 개발 규칙은 [CLAUDE.md](./CLAUDE.md)에 있다. 축소 불가 규칙 5개를 먼저 읽을 것.
> 상세 명세는 `docs/` — 충돌 시 `docs/01-scope.md`가 우선한다.

## 스택

Next.js 16 (App Router) · Vercel · Supabase (PostgreSQL) · Claude API (Opus 5) · 읽기 전용 도구 5종

판단은 4계층으로 나뉘고 계층 사이에 편향 차단 경계가 있다. 판단 계층은 이용자 진술 원문을
받지 않으며, 그 격리는 프롬프트가 아니라 타입으로 강제한다 (`docs/05-auth.md` P-401).

```
① 상담  되묻기 · 슬롯 확정 · 사실관계 정제
② 조사  도구 5종 오케스트레이션
━━━ 편향 차단 경계 ━━━
③ 판단  정제 사실관계 + 근거만 수신 → 결론 + 확신도
④ 안내  용어 풀이 · 다음 행동 (판단 수정 불가)
```

## 모델을 부르는 곳과 부르지 않는 곳

런타임에 Claude를 부르는 것은 **판단 파이프라인 4계층뿐**이다. 나머지 화면은 모델을
하나도 부르지 않는다 — 사전 점검(S-02) · 분쟁 패턴 지표(S-09~12) · 해피콜 연습(S-14) ·
검증 결과(S-06) · 데모 3종.

**뺀 것이지 안 쓴 것이 아니다.** 이 화면들이 보여주는 집계·점검 문장·시나리오는 틀리면
이용자가 잘못된 대비를 하는 자리라, 런타임 생성이 아니라 사전 집계표와 코드 상수에서
읽는다. 모델이 집계를 추정하면 그 자리가 그대로 환각 위험이 되고(F-603), 모델 장애 때
예방 축 전체가 같이 죽는다.

**대신 그 데이터를 모델이 만들었다.** 구조화한 결정서 388건에 쟁점·상품군·판매채널·
소비자 특성을 분류해 붙인 것이 [`scripts/classify_corpus.py`](scripts/classify_corpus.py)
이고(`label_source='MODEL'`), 그 라벨을 정식 결정서 기준으로 교차집계해 `risk_patterns`를
만드는 것이 [`scripts/aggregate_patterns.sql`](scripts/aggregate_patterns.sql)이다.
즉 모델은 **빌드 타임에 쓰고 런타임에는 굳힌 값을 읽는다.**

**부착률은 축마다 다르다** — 388건 중 channel 125 · traits 39 · compensation_rate 35
(`docs/10-db.md` v20260830-r03). 전 건에 모든 라벨이 붙어 있지 않으므로 「사건마다 읽어
붙였다」로 쓰지 않는다. 집계 모집단(`stat_basis`)은 화면이 DB에서 읽어 그대로 표시하고,
문서에 숫자로 박지 않는다.

이 집계는 (상품군 × 채널 × 특성) → 쟁점별 인용·기각 건수 형태다. 결정서는 개별 문서로만
공개돼 있어 **이 축으로 묶인 공개 집계는 조사 범위에서 확인하지 못했다** — 「없다」가
아니라 「찾지 못했다」로 적는다. 이용자가 검색으로 도달하기 어려운 자리라는 것이 예방
축의 근거다.

## 검증 결과

제품을 그대로 태워 검증셋 120건을 **두 번** 측정한 값이다 (2026.08.31 공식 런).
같은 입력에서도 확신도가 흔들려 커버리지가 24~33%를 오가기 때문에, 한 번 잰 값을
걸면 그 흔들림이 수치 뒤에 숨는다.

| 지표 | 값 (2회 합산) | 95% 신뢰구간 | 회차별 |
|---|---|---|---|
| 결론을 냈을 때 정확도 | 92.3% (60/65) | 83.2 ~ 96.7 | 93.1% · 91.7% |
| 결론을 내는 비율 | 27.1% (65/240) | 21.9 ~ 33.0 | 24.2% · 30.0% |
| 두 번 모두 결론이 선 사건 | 25/120 중 24건 적중 (96.0%) | 80.5 ~ 99.3 | 한쪽만 결론 15건 |
| 유보한 사건의 정확도 | 64.6% (113/175) | 57.2 ~ 71.3 | 62.6% · 66.7% |

확신이 서지 않으면 결론을 내지 않는다. 그래서 커버리지가 낮고, 그것이 설계다.
유보 구간 정확도는 이용자에게 불리한 수치지만 함께 공개한다.
합산 240표본은 독립 240건이 아니라 120건을 두 번 잰 것이라, 회차별 값을 함께 읽는다.

**커버리지를 올리려는 개입을 세 번 실험해 세 번 기각했다.** 기준은 결과를 보기 전에
고정했고 결과를 본 뒤 고치지 않았다. 그중 둘은 «원래 유보하던 사건을 결론 내게 만든
구간»에서만 무너졌다 — 유보되는 사건이 실제로 더 어렵다는 뜻이고, 확신도 임계 4점이
난이도 경계에 서 있다는 실측 근거다. 이 부정 결과도 화면에 공개한다.

**안전성 시험** — 프롬프트 인젝션 7/7 · PII 변형 9/9 · 유도 질문 6/6 방어.
이 시험이 실제 구멍 하나를 찾았다(주민번호 앞자리가 하이픈 없이 오면 미검출 —
같은 날 수정). 공격 문안을 직접 썼다는 한계도 함께 공개한다.

수치의 단일 출처는 DB `validation_stats`이고 원자료는 `measure/`에 있다. 화면·문서와
어긋나면 안 된다. 화면 [`/verification`](https://precase.vercel.app/verification)에는
검증하지 못한 항목과 기각한 실험도 함께 싣는다.

이전 단일 런(90%·33.3%)은 이 공식 런으로 대체됐다 — 다른 실험이 아니라 같은 과제의
재측정이다. 그와 별개로 기획서에 실린 84%·66~71%는 **다른 과제를 잰 실험값**이다.
완결된 조정례 결정서를 넣고 위원회 결정을 예측한 실험이라 제품 성능으로 인용하지
않는다. 기록으로는 보존한다.

## 개발 환경

```bash
npm install
cp .env.example .env.local   # 값 채우기
npm run dev
```

```bash
npm test           # vitest. DB·외부 API 테스트는 자격증명이 없으면 skip
npm run typecheck  # next typegen && tsc --noEmit
npm run build      # 머지 전 필수
```

모델·법제처 API·DB를 실제로 치는 테스트는 기본 실행에서 건너뛴다. 돌리려면 `PRECASE_LIVE=1`.

DB 스키마는 `supabase/migrations/`에 순서대로 있다. 코퍼스 재적재는 `scripts/load_corpus.py`
(게이트 포함, `--dry-run` 지원).

## 저장소 읽는 법

**커밋 1개 = 계획의 항목 1개.** 기능 작업은 브랜치에서 하고, 끝난 뒤 이슈 → PR(`Closes #N`)
→ squash merge 순으로 정리한다. 그래서 `main`의 커밋 하나가 곧 완결된 작업 단위다.
이슈는 착수 전에 만들지 않는다. 계획의 정본은 `HANDOFF.md`이고 이슈는 끝난 작업의 기록이다.

**PR 본문에는 설계 판단과 확인 방법을 적는다.** 갈림길에서 버린 선택지와 그 이유, 그리고
무엇으로 확인했는지가 거기 있다.

### 라벨

| 유형 | |
|---|---|
| `feat` | 새 기능 — 명세의 F/S/SR 항목 구현 |
| `fix` | 결함 수정 |
| `chore` | 빌드·설정·정리 |
| `docs` | 명세·인수인계 문서 갱신 |
| `refactor` · `test` | 구조 개선 · 테스트 보강 |

| 명세 영역 | 대응 문서 |
|---|---|
| `SR 범위` | `docs/01-scope.md` (SR-xxx) |
| `F 기능` | `docs/02-functional.md` (F-xxx) |
| `DR 데이터` | `docs/03-data.md` (DR-xxx) |
| `S 화면` | `docs/04-screen.md` (S-xx) |
| `E 연동` | `docs/06-integration.md` (E-xx) |
| `N 비기능` | `docs/08-nfr.md` (N-xxx) |
| `DB` | `docs/10-db.md` |

영역 라벨은 명세 문서와 1:1이다. 이슈를 `S 화면`으로 거르면 화면 요구사항에
관한 작업만 남고, 제목 괄호의 `(SR-202)`로 해당 문서의 항목까지 바로 간다.

| 특수 | |
|---|---|
| `축소 불가` | 일정이 밀려도 빼지 않는 항목 (예: S-06 검증 결과 화면) |
| `배포 조건` | 통과하지 못하면 배포할 수 없는 게이트 (예: PII 미검출 0건) |

### 제목 규칙

- 이슈 — `[FEAT] 무엇을 만드는가 — 왜 필요한가 (명세 ID)`
- PR — `feat(fe): 무엇을 했는가 (명세 ID)`. 영역은 `be`(백엔드) / `fe`(화면)

괄호 안의 `SR-202`·`F-503` 같은 ID는 `docs/`의 요구사항 번호다. 이슈에서 명세로,
명세에서 코드로 따라갈 수 있다.

규칙의 근거와 다른 프로젝트에 옮겨 쓰는 방법은
[`.github/ISSUE_PR_PLAYBOOK.md`](./.github/ISSUE_PR_PLAYBOOK.md)에 정리해 뒀다.

### 머지 규칙

- `main`이 배포 브랜치다. Vercel Production이 여기 물려 있어 머지가 곧 배포다
- 머지 전 `npm test` · `npm run build` 통과가 조건이고 PR 체크가 이를 검사한다
- 머지해도 브랜치를 지우지 않는다. 작업 이력을 남긴다
